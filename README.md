## Задача 1. Кластеризация

### Предлагаемое решение

Для развёртывания, запуска и управления микросервисными приложениями
предлагается использовать **Kubernetes**. Это платформа оркестрации
контейнеров, которая позволяет централизованно управлять приложениями,
распределять нагрузку между экземплярами сервисов, выполнять
автоматическое масштабирование и обеспечивать отказоустойчивость.

В качестве дополнительных компонентов предлагается использовать:

-   **Container Registry** --- хранилище собранных Docker-образов.
-   **Ingress Controller** --- входная точка для внешнего
    HTTP/HTTPS-трафика.
-   **Kubernetes Service** --- механизм обнаружения сервисов и
    распределения запросов внутри кластера.
-   **Metrics Server и Horizontal Pod Autoscaler (HPA)** --- сбор метрик
    и автоматическое масштабирование количества экземпляров приложений.
-   **Cluster Autoscaler** --- автоматическое увеличение или уменьшение
    количества узлов кластера, если это поддерживается используемым
    облачным провайдером.
-   **ConfigMap и Secret** --- хранение конфигурации и чувствительных
    данных.
-   **HashiCorp Vault** (как дополнительный компонент) ---
    централизованное безопасное хранение секретов и управление доступом
    к ним.

### 1. Поддержка контейнеров

Каждый микросервис упаковывается в отдельный Docker-образ. Образы
собираются в процессе CI/CD и публикуются в Container Registry.

Kubernetes получает нужный образ из реестра и запускает его в контейнере
внутри Pod. Pod является минимальной единицей развёртывания в Kubernetes
и может содержать один или несколько тесно связанных контейнеров.

Для управления приложениями используются ресурсы Kubernetes, например:

-   **Deployment** --- описание желаемого состояния приложения: образ,
    количество реплик, настройки и стратегия обновления.
-   **Pod** --- запущенный экземпляр приложения.
-   **StatefulSet** --- управление приложениями, которым необходимы
    стабильные сетевые идентификаторы или постоянное хранилище.
-   **DaemonSet** --- запуск вспомогательного компонента на каждом или
    выбранных узлах кластера.

Таким образом, приложения запускаются в изолированных контейнерах, а
Kubernetes следит за тем, чтобы фактическое состояние соответствовало
заданному.

### 2. Обнаружение сервисов и маршрутизация запросов

Для взаимодействия микросервисов внутри кластера используются объекты
**Service** и встроенный DNS Kubernetes.

Каждому Service назначается постоянное DNS-имя. Другие приложения могут
обращаться к нему по этому имени, не зная IP-адресов отдельных Pod. Если
Pod пересоздаётся и получает новый IP-адрес, Service продолжает
направлять запросы на доступные экземпляры приложения.

Для входящего внешнего HTTP/HTTPS-трафика используется **Ingress
Controller**. Он принимает запросы и направляет их к нужным Service на
основании доменного имени и пути запроса. Например:

-   `api.example.com/users` --- сервис пользователей;
-   `api.example.com/orders` --- сервис заказов.

Для внутренних запросов используются ClusterIP Service. Они доступны
только внутри кластера и не публикуются напрямую в интернет.

### 3. Горизонтальное масштабирование

Горизонтальное масштабирование позволяет увеличивать или уменьшать
количество одновременно работающих экземпляров микросервиса.

В Kubernetes для этого используются Deployment и параметр `replicas`.
Например, для сервиса заказов можно задать три реплики. Kubernetes
запустит три Pod и будет поддерживать указанное количество экземпляров.

При увеличении нагрузки количество реплик можно изменить вручную.
Service автоматически распределит запросы между доступными Pod.

Пример фрагмента конфигурации Deployment:

``` yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders
spec:
  replicas: 3
  selector:
    matchLabels:
      app: orders
  template:
    metadata:
      labels:
        app: orders
    spec:
      containers:
        - name: orders
          image: registry.example.com/orders:1.0
          ports:
            - containerPort: 8080
```

### 4. Автоматическое масштабирование

Для автоматического масштабирования количества экземпляров приложения
используется **Horizontal Pod Autoscaler (HPA)**.

HPA получает метрики, например загрузку CPU и памяти, и сравнивает их с
заданными целевыми значениями. Если нагрузка превышает целевой уровень,
Kubernetes увеличивает количество Pod. Когда нагрузка снижается,
количество экземпляров может быть уменьшено в пределах заданных
ограничений.

Пример конфигурации HPA:

``` yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: orders
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: orders
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

Для работы HPA необходим источник метрик, например Metrics Server.

Если ресурсов на узлах кластера недостаточно для размещения новых Pod,
**Cluster Autoscaler** может добавить узлы. При снижении потребности в
ресурсах он может удалить незагруженные узлы. Таким образом, HPA
масштабирует приложения на уровне Pod, а Cluster Autoscaler ---
инфраструктуру на уровне узлов.

### 5. Разделение внешних и внутренних ресурсов

Для разделения ресурсов, доступных извне и только внутри системы,
предлагается использовать разные типы Kubernetes Service и отдельные
правила сетевого доступа.

-   **ClusterIP** --- используется для внутренних сервисов. Доступен
    только изнутри кластера.
-   **LoadBalancer** --- может предоставлять внешний IP-адрес через
    интеграцию с облачным провайдером.
-   **Ingress** --- организует контролируемый доступ к
    HTTP/HTTPS-сервисам через Ingress Controller.

Внешние запросы поступают через LoadBalancer на Ingress Controller,
после чего маршрутизируются к нужным внутренним Service. Базы данных,
очереди сообщений и внутренние API не должны публиковаться напрямую во
внешнюю сеть.

Дополнительно следует применять **NetworkPolicy**, чтобы ограничивать
сетевое взаимодействие между Pod и разрешать только необходимые
соединения. Например, доступ к базе данных можно разрешить только
определённым микросервисам.

Для более строгой изоляции можно использовать отдельные Namespace для
разных окружений или групп приложений, например `development`, `staging`
и `production`. При необходимости инфраструктуру можно разделить на
отдельные кластеры.

### 6. Конфигурация приложений и хранение секретов

Kubernetes позволяет передавать настройки приложения через переменные
среды.

Для обычных параметров конфигурации используются **ConfigMap**.
Например, там можно хранить адрес сервиса, режим работы приложения или
название базы данных.

Для чувствительных данных используются **Secret**. В них можно хранить
пароли, токены, ключи доступа и другие секреты. Контейнер получает
необходимые значения через переменные среды или подключённые файлы.

Пример использования ConfigMap и Secret в Deployment:

``` yaml
env:
  - name: APP_MODE
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: mode
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: db-secret
        key: password
```

Для production-среды рекомендуется дополнительно использовать
**HashiCorp Vault**. Он обеспечивает централизованное хранение секретов,
контроль доступа и аудит обращений. Получение секретов из Vault можно
организовать с помощью соответствующего интеграционного механизма,
например External Secrets Operator.

Важно учитывать, что Kubernetes Secret сам по себе не гарантирует
полноценную защиту данных: значения в манифестах могут быть представлены
в Base64. Поэтому необходимо включить шифрование секретов в хранилище
Kubernetes, ограничить доступ с помощью RBAC, не хранить секреты в Git и
использовать минимально необходимые права.

### Принцип взаимодействия компонентов

Общий процесс работы предлагаемой инфраструктуры выглядит следующим
образом:

1.  Разработчик отправляет изменения в Git.
2.  CI/CD собирает Docker-образ микросервиса, запускает проверки и
    публикует образ в Container Registry.
3.  Средства CI/CD или GitOps обновляют описание Deployment в
    Kubernetes.
4.  Kubernetes загружает образ и запускает Pod на доступных узлах
    кластера.
5.  Внутренние микросервисы находят друг друга через Service и DNS
    Kubernetes.
6.  Внешние HTTP/HTTPS-запросы поступают через LoadBalancer и Ingress
    Controller, а затем направляются к нужным сервисам.
7.  HPA отслеживает метрики и при необходимости изменяет количество Pod.
8.  Cluster Autoscaler при нехватке вычислительных ресурсов добавляет
    узлы кластера.
9.  Приложения получают обычные настройки из ConfigMap, а чувствительные
    данные --- из Secret или Vault.

### Обоснование выбора

Kubernetes выбран по следующим причинам:

-   **Поддержка контейнеров.** Kubernetes изначально предназначен для
    управления контейнеризированными приложениями и поддерживает
    стандартные контейнерные среды выполнения.
-   **Обнаружение сервисов.** Встроенные Service и DNS позволяют
    микросервисам взаимодействовать друг с другом без ручного управления
    IP-адресами.
-   **Маршрутизация запросов.** Ingress Controller обеспечивает
    централизованную обработку внешнего HTTP/HTTPS-трафика.
-   **Горизонтальное масштабирование.** Количество экземпляров
    приложения можно изменять вручную или автоматически.
-   **Автоматическое масштабирование.** HPA масштабирует приложения по
    метрикам, а Cluster Autoscaler при необходимости масштабирует
    инфраструктуру.
-   **Сетевая изоляция.** Типы Service, Namespace и NetworkPolicy
    позволяют разделять внешние и внутренние ресурсы и ограничивать
    доступ.
-   **Управление конфигурацией и секретами.** ConfigMap и Secret
    позволяют передавать настройки приложения, а интеграция с Vault
    повышает безопасность хранения чувствительных данных.
-   **Отказоустойчивость и обновления.** Kubernetes контролирует
    состояние Pod, перезапускает неисправные экземпляры и поддерживает
    управляемое обновление приложений.

### Вывод

Для крупной компании с микросервисной архитектурой целесообразно
использовать Kubernetes в качестве основной платформы оркестрации
контейнеров. В сочетании с Container Registry, Ingress Controller, HPA,
Cluster Autoscaler, ConfigMap, Secret и HashiCorp Vault это решение
покрывает требования задачи.

Предложенная архитектура позволяет централизованно развёртывать и
сопровождать микросервисы, обеспечивать обнаружение сервисов и
маршрутизацию запросов, разделять внутренние и внешние ресурсы, а также
масштабировать приложения и вычислительную инфраструктуру в зависимости
от нагрузки.
